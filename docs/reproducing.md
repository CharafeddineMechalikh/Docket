# Reproducing results

This page states how to build the simulator, run its tests, regenerate the measured numbers, and
check that two runs of the same configuration produce the same artifacts. It is the reference for
anyone auditing a number that appears in the [README](../README.md) or in a paper that cites this
repository.

## What you need

| Tool | Version | Why |
|---|---|---|
| JDK | 11 or newer | The bytecode target is 11; Maven 3.8.1 here runs on JDK 17, and the quoted console runs use a JDK 23 runtime |
| Maven | 3.6 or newer (tested on 3.8.1) | Resolves PureEdgeSim, JUnit 5 and the build plugins |
| Python | 3.x with `matplotlib` | Only for `scripts/plot_sweeps.py`; the simulator itself does not need Python |
| GPU | none | The device is a profile, not hardware |

The PureEdgeSim engine is a normal Maven dependency, so the first build downloads it. Nothing is
compiled from a local checkout and no environment variable points at one.

## Build

```bash
mvn clean package
```

This writes three things into `target/`:

- `docket-1.0.1.jar`, with the main class and the implementation version in its
  manifest, so `java -jar ... --version` reports the artifact's own version;
- `lib/`, the runtime dependencies, filled by `maven-dependency-plugin`;
- `docket-1.0.1-javadoc.jar`, attached by the `attach-javadocs` execution.

Run the jar on its own:

```bash
java -jar target/docket-1.0.1.jar scenarios/single-gpu-poisson.properties
```

The API documentation is generated by:

```bash
mvn javadoc:javadoc
```

which writes browsable pages to `target/site/apidocs/`. The plugin runs `doclint` with
`all,-missing,-html`: signatures and references are checked, the `@param`, `@return` and `@throws`
completeness check is off because it is enforced by review rather than by the build, and the HTML
check is off because the GPL header of every file contains a literal URL in angle brackets, which
the strict check reads as a malformed tag.

## Test

```bash
mvn test
```

The suite is 140 JUnit 5 tests and takes about fifteen seconds on the development machine. It runs
the real engine end to end; there are no stubs and no simulated success. The layers are described in
the [README](../README.md#testing). Three of them matter when checking a result:

- **Invariant** re-derives the accounting of a finished run from its exposed counters. A request is
  terminal exactly once, device energy equals the sum over replicas and is at least the idle floor,
  pooled statistics equal the sums over the request rows, and no reservation exceeds the pool.
- **Regression** pins the two committed scenarios to the numbers measured on this branch, per
  repetition, with an energy tolerance of 0.5 J and a TTFT tolerance of 1e-4 s.
- **Integration** checks that the same seed reproduces a run and that a different repetition index
  does not.

A legitimate change may move the regression anchors; the point is that it has to move them
deliberately, by updating `src/test/java/com/mechalikh/docket/regression/ScenarioRegressionTest.java`
in the same commit, rather than silently.

## Run the committed scenarios

```bash
java -jar target/docket-1.0.1.jar scenarios/single-gpu-poisson.properties
java -jar target/docket-1.0.1.jar scenarios/loaded-7b-memory-pressure.properties
```

Both files already set `experiment.repetitions=3`, `experiment.seed=1` and
`experiment.outputDir=target/experiments`, so the artifacts land in
`target/experiments/<experiment.name>/` and the console prints the three-repetition table quoted in
the README. Useful overrides:

| Flag | Effect |
|---|---|
| `-r N` | Repetitions, replacing `experiment.repetitions` |
| `-s N` | Base seed, replacing `experiment.seed` |
| `-o DIR` | Output root, replacing `experiment.outputDir` |
| `-D key=value` | Any scenario property; repeatable |
| `-q` | Write the artifacts without the console report |

`-D` is applied last, after the file and before `-r`, `-s` and `-o`, which is the order the
[configuration page](configuration.md#precedence-and-overrides) documents.

## Regenerate the measured sweeps

`scripts/run_sweeps.sh` re-runs the 19 configurations quoted in the paper, three repetitions each,
plus the two baselines:

```bash
scripts/run_sweeps.sh                 # writes under target/sweep
scripts/run_sweeps.sh target/sweep2   # or under a root of your choice
```

The sweep varies the offered rate (`15` to `480` requests/min), the batch ceiling (`4` to `64`), the
prefill chunk (`0` to `2048` tokens), the block size (`8`, `16`, `32`) and preemption on the loaded
scenario, and then runs the light and loaded baselines. Each configuration is a separate JVM, so a
failure prints `FAILED <name>` and the script continues; it ends with `SWEEP_DONE fail=0`, and any
other value means at least one run failed.

The artifact layout follows the simulator, which appends the experiment name to the output
directory: a configuration named `rate60` run with `-o target/sweep/rate60` writes
`target/sweep/rate60/rate60/summary.csv` and `rep01/`, `rep02/`, `rep03/` beside it.

Then draw the figures:

```bash
python scripts/plot_sweeps.py            # target/sweep -> target/figures
python scripts/plot_sweeps.py target/sweep2 target/figures2
```

The script reads every `summary.csv` under `<root>/<prefix>*/*/`, averages each numeric column over
the repetitions, and writes `fig_sweep_rate.pdf` and `fig_sweep_batch.pdf` (plus PNGs). Nothing is
interpolated or smoothed. If a sweep is missing, it prints `missing sweep data for ...` and writes
nothing for that figure rather than plotting a partial curve.

The plots are figures of the analytical model, not of hardware. The batch figure annotates the
cache-imposed ceiling of 19 sequences, which is the number the [memory page](memory.md) derives for
the loaded scenario.

## Replay the public traces

The four committed trace windows are replayed and reconciled with:

```bash
bash examples/real-traces/run_replays.sh                 # writes target/trace-replays
bash examples/real-traces/run_replays.sh target/replays2 # or under a root of your choice
```

Each scenario runs in its own JVM without `-q`, so the script saves the full console report as
`<root>/<name>.console.txt` beside the artifacts. `verify_replays.py` then compares
`<root>/<name>/rep01/requests.csv` with `examples/real-traces/data/<name>.csv` as a multiset of
(arrival, prompt, requested output, service class). A run that dropped, duplicated or rescaled a
request fails the check; a successful run ends with `REPLAY_CHECK OK` and four `OK` lines.

The archived captures and summaries are in `examples/real-traces/results/`; the upstream file each
window was cut from, its SHA-256, and the transformations applied are in
`examples/real-traces/data/manifest.json`. To rebuild a window:

```bash
python examples/real-traces/fetch_traces.py       # target/traces-cache, gitignored
python examples/real-traces/convert_traces.py     # rewrites data/ and manifest.json
```

The replays are one repetition at seed 1 and contain no random draws in the workload: the arrival
instants, prompt lengths and generated lengths are read from the file. They are therefore
byte-reproducible by construction, and the reconciliation is the stronger check.

## Determinism

A run is a pure function of the scenario file, the overrides and the seed. The engine does not read
the wall clock, does not iterate over a hash container whose order can change, and does not
parallelise a repetition. Each repetition gets a fresh event engine and fresh entities, and the
scenario plan is rebuilt for it, because a PureEdgeSim sampler binds the thread's random generator
when it is created.

Every repetition starts from the configured base seed, and the repetition index salts the stream,
so repetition 2 draws differently from repetition 1 while both remain tied to that base seed.
Repetitions are numbered from one and run in order.

What this guarantees, and what it does not:

- **Same JVM and platform.** Two runs produce byte-identical artifacts. You can check it directly:

  ```bash
  java -jar target/docket-1.0.1.jar -q -o target/check/first scenarios/loaded-7b-memory-pressure.properties
  mv target/check/first target/check/keep
  java -jar target/docket-1.0.1.jar -q -o target/check/first scenarios/loaded-7b-memory-pressure.properties
  diff -r target/check/first target/check/keep && echo identical
  ```

- **A different JDK.** Floating-point addition and multiplication are exact operations, but
  transcendental functions such as `log` and `exp` are supplied by the platform library and may
  differ in the last bit between implementations. A distribution sampler uses them, so a different
  JDK can in principle move a boundary case: a prompt that fits by one block against one that does
  not. The committed captures do reproduce across the two JDKs used here, the JDK 17 that Maven
  runs the tests on and the JDK 23 runtime, but results are still compared like for like on a
  pinned JDK, and a moved regression anchor after an upgrade is investigated rather than assumed
  harmless.

- **A different seed.** Everything drawn changes: arrival instants, prompt and output lengths, and
  the jitter added to a correlated output. The regression anchors hold for seed 1 only; the
  standard error printed in the console is the measure of how far a seed can move an aggregate, and
  it is why the committed scenarios run three repetitions instead of one.

- **Time.** The simulated clock is separate from the wall clock, so a slower machine takes longer to
  produce the same numbers. `samples.csv` is sampled on the simulated clock and is deterministic as
  well.

## Which numbers are which

The README quotes three kinds of numbers and marks them:

- **Freshly measured.** The console blocks and the per-scenario tables were produced by the
  commands above on this branch, at seed 1 with three repetitions, and are pinned by the regression
  tests.
- **Replayed.** The four trace tables replay recorded arrivals and lengths, and the reconciliation
  proves the traffic is the trace's. Their latencies and energy are still analytical, because the
  device and the cost model are the synthetic ones; the trace makes the workload measured, not the
  service time.
- **Analytical.** The worked arithmetic on the [cost model](cost-model.md) and [memory](memory.md)
  pages is computed from the formulas and the scenario settings, not read from a run. Where a run
  and the arithmetic can be compared, they agree; where they cannot, the page says which one it is.

No number in this repository is calibrated against a real accelerator. Every scenario prints
`overall provenance : synthetic`, and the artifacts carry `cost_calibrated=no` on every row, so a
number cannot travel far from that label without being questioned.

## When a run does not do what you expect

| Symptom | Cause |
|---|---|
| `warning: the scenario sets "..." but nothing reads it` | A misspelled or retired key; the run continues with the default. The [configuration page](configuration.md) lists every key |
| Exit code `2` | Usage error: unknown flag, missing scenario file, unreadable path |
| Exit code `3` | The scenario does not load: a missing required setting, a value out of range, an unreadable or malformed trace. The message names the key or the trace line |
| Exit code `4` | The run failed: an invariant was broken, or an artifact could not be written. The message says which |
| No console output | `-q` was given; the artifacts are still written |
| `missing sweep data for fig_sweep_rate` | `run_sweeps.sh` did not finish, or its output root is not the one passed to the plot script |
| An empty percentile shown as `-` | No request reached that phase; a metric with no observation has no percentile, see [Metrics](metrics.md#per-request-metrics) |
